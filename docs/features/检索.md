# 检索（三路混合）

## 1. 这个功能对用户是什么

你问一句话，它从你半年写下的东西里挑出**最相关的那几条**，递给你。

它不像搜索框——你不需要想好关键词。你说「我好累」，它能翻出你 40 天前那条「面试前失眠，觉得自己什么都准备不好」，哪怕那条记录里根本没有「累」这个字。

这个功能本身不产出人话（那是 [`对话.md`](对话.md) 的事）。它的产物是一小段记录清单，附在对话的上下文里。

## 2. 一次调用的完整路径

```
life ask "我好累，感觉半年了什么都没做成"
  ↓
① 把整句拆成片段：["我好累", "感觉半年了什么都没做成"]
  ↓
② 三路并行找（每路各取 10 条）
   路 1 向量    把查询也变成向量，跟库里每条记录算余弦相似度，取 > 0.2 的
   路 2 全文+实体 FTS5 全文搜每个片段 + 在 anchors（技术名/人名/链接）里找
   路 3 结构    SQL 直达：
                 查询里有情绪词 → valence < -0.5 ORDER BY ts DESC
                 查询里有时间词 → 去年同一个日子
                 查询里有「怎么恢复」 → 低谷之后的第一个 done
  ↓
③ 合并：RRF（倒数名次融合）——被两路同时捞到的排最前面
  ↓
④ 过滤：private = 1 的记录在每一路都被挡掉（§8）
  ↓
⑤ 三路全空 → 兜底给最近 3 条，不让对话没有上下文
  ↓
⑥ 取前 5~8 条交给对话模块
```

## 3. 关键代码在哪

```
life/retrieve.py::召回()         三路的调度与合并，返回（结果，诊断）
life/retrieve.py::_向量路()      余弦相似度（朴素实现，没用 sqlite-vec 扩展）
life/retrieve.py::_全文路()      FTS5 + LIKE 兜底 + anchors 实体命中
life/retrieve.py::_片段们()      把整句话拆成可搜的片段
life/retrieve.py::_结构路()      §4.3 里那三条 SQL
life/retrieve.py::_合并()        RRF 融合与去重
life/retrieve.py::最近几天()     §4.4 上下文里的「最近三天」
life/index.py::读全部向量()      向量存成 float32 BLOB，读进内存再算
life/cli.py::_打印召回()         `--dry-run` 的实现，用来判断「它到底翻没翻对」
```

## 4. 为什么这么设计

最容易被做错的决定是：**一路检索够不够？**

「把所有记录塞给大模型，让它自己挑」听着最省事，但它被否掉了：
- 几百条记录塞不进上下文（§3.1 明确说「永远不要把全部记录塞进上下文」）；
- 就算塞得进，一次对话几万 token，成本立刻失控；
- 而且它挑不准——模型没有「时间感」，你不知道它凭什么选了这几条。

第二个决定：**为什么非要第三路（结构检索）？**
因为人崩溃时问的不是搜索词。他想问的是「我以前也这样过吗，后来怎么好的」。这个问题文字上完全不像，向量也未必抓得住（「我好累」和「面试前失眠」语义差很远）。只有 SQL 能回答：「给我所有 valence < -0.5 的记录，按时间倒序」。

第三个决定：**用 RRF 而不是先接 rerank。**
§4.3 说「rerank 取前 5~8 条」。但 rerank 要额外一个接口，而现在连向量接口都没有。RRF 只用名次、不用分数，天然能把「多路都命中」的记录顶上去，零成本。等有了 rerank 接口再加一层，不影响现在的结构。

## 5. 已知限制

- **向量路现在跑不起来**：你本机的接口没有 embedding 模型。代码写好了，配上 `tasks.embed` 就能用；不配时它会跳过并明说，不会静默降级。
- 向量是**朴素余弦**，没有用 `sqlite-vec` 扩展；几千条没问题，十万条会慢。
- FTS5 用的 trigram 分词，**查询片段至少 3 个字**才走索引，更短就退回 `LIKE`（慢一点，但能用）。
- 整句提问（比如「我感觉这半年什么都没做成」）在全文路上基本命中不了——这是原文匹配的固有限制，得靠向量路。所以现在会提示用户「整句提问主要靠向量路」。
- 结构路靠一张手写关键词表（情绪词/时间词/恢复词）。表里没有的说法就走不到对应 SQL，比如「心里堵得慌」现在不触发情绪检索。
- 没有实现真正的降权/去重：同一条记录被三路各捞一次，也只算一份分数。
