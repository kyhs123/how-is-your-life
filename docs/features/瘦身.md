# 瘦身（life tidy）

## 1. 这个功能对用户是什么

用久了 vault 会「长胖」，但长胖的东西大多是**可以重建的**。瘦身只清这些，**一条记录都不动**。

```powershell
life tidy --dry-run     # 先看能清多少，一个文件都不动
life tidy               # 真清（默认清 90 天前的缓存）
life tidy --days 30     # 换个天数
```

页面上也有：**设置 → 瘦身**（后台任务，页面自刷）。设置页顺便告诉你当前占用：

```
抽取缓存 = 15 个（30.9KB）｜可清 0 个
媒体全文 = 2 个｜孤儿 0 个（0B）
```

**能清的**：90 天前的抽取缓存、确认没人引用的 media 全文、删完留下的空目录。
**绝不碰**：`now/`（记录）、`chapters/`、`goals/`、`core.md`、`portrait/`、还有主的 media。

## 2. 一次调用的完整路径

```
life tidy
  ↓
① 扫描：缓存文件数/大小、其中超过 N 天的、media 文件数、孤儿
② 打印数字（--dry-run 就停在这里）
③ 真删：
     缓存：mtime 早于 N 天前的 → 删
     孤儿：关联表里登记过、但那些记录**一个都不存在了**的 media → 删
④ 收掉空目录（桶目录、media）
⑤ 打印「清掉几个、共多少 KB」
```

```
vault/缓存/抽取/<指纹前两位>/<指纹>.json   ← 分 256 个桶
vault/media/关联.json                      ← 记录：哪个全文属于哪些记录
```

## 3. 关键代码在哪

```
life/tidy.py::扫描()          只数不改（干跑用的就是它）
life/tidy.py::执行()          真删 + 收空目录
life/tidy.py::孤儿media()     保守判定（见下面「为什么」）
life/extract.py::缓存路径()   按指纹前两位分桶
life/extract.py::读缓存()     读到老格式会自动搬进桶
life/store.py::写media关联()  写完全文就登记归属
life/server.py::_作业瘦身()   网页上的按钮
life/cli.py::tidy             命令本身
```

## 4. 为什么这么设计

**① 为什么缓存要分桶？**
缓存是「每条内容一个 json」。一天五条，五年九千个文件——**全堆在一个目录里**，Windows 列目录会卡，遍历也慢。按指纹前两位分成 256 个桶，单目录最多几十个。老文件不用手动迁移：第一次读到就顺手搬。

**② 为什么孤儿判定要这么保守？**
第一版按「文件名 = 记录 id」判断，结果**把简历的两份全文判成了孤儿**——因为 media 的文件名用的是「输入 id」，而记录用的是「记录 id」，一条输入可能拆成好几条记录，两套 id 根本对不上。

现在改成：**只删「关联表里登记过、且那些记录一个都不在了」的文件**；没登记过的一律不动，只在报告里说「有 N 个分不清归属」。宁可留几个垃圾，也不要删掉一张截图唯一的 OCR 全文。

**③ 为什么不做自动清理？**
后台偷偷删东西最容易让人不信任。清缓存这种动作必须由人发起，而且默认**先干跑看数字**。

## 5. 已知限制

- 缓存「过期」看的是**文件修改时间**，不是内容创建时间——你手动拷动过文件就可能判断不准。
- 关联表是这一版才有的；**更早的 media 文件没有登记**，所以永远不会被自动清理（会一直显示「未登记 N 个」）。要清就手动删。
- 不清理 `inbox/`（那是没抽成的内容，属于「还没处理完」，删了等于丢用户输入）。
- 不清理 `review/`（生成过的回顾 HTML）——想删自己删，它们不大。
- 不会压缩、不会归档旧月份目录：`now/2023-01/` 会一直在，这是故意的（那是你的记录，不是缓存）。
