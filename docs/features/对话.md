# 对话（life ask）

## 1. 这个功能对用户是什么

你难受的时候，敲一句「我好累，感觉半年了什么都没做成」。

它不回你「你已经很棒了」。它会翻出你自己的记录，把证据摆到你面前：

> 累是真的。但「什么都没做成」这个结论我不认——2026-11-22 你跑了 5 公里，配速 6 分，比上个月还快了一点，这不是没做成。2026-09-26 你也说过「我是不是就这样了」，那次记录里只有崩溃；这次往前翻，至少还有一条往上走的。要不要今晚只把跑步那条备注成「比上个月快」，别的先不动？不想弄就睡。

**这就是这个产品存在的理由：不是记录，是在你需要的时刻把证据递给你。**

## 1.5 说话的温度（2026-11-25 调整）

第一版把「不许空泛安慰」写得太硬，模型就变成了**在读台账**——「2026-11-25 你调 OAuth 卡在…；同一天你把订单模块…」。
项目所有者一句「太生硬了」，点出了真正的问题：**不哄人 ≠ 像审计报告**。

改了三处：

| 改了什么 | 之前 | 现在 |
|---|---|---|
| prompt 的人设 | 「不是安慰者，是把证据递回他手上」 | 「既了解他、又不哄他的长辈：老师说人话的那种，父亲会认真听完再开口的那种」 |
| 回答的结构 | 三条硬要求（日期/对比/下一步） | 加了「开头先接住一句」和「建议要有分量」——**只给一个，但要具体到今晚或这周** |
| 随机度 | 全局写死 `temperature: 0.2` | **按任务配**：抽取 0.2（要稳），对话 **0.7**（要有温度），画像 0.5 |

**温度写死 0.2 是主因之一**：同样的 prompt，0.2 会选出最「安全」的句式，读起来像公文。现在 `providers.yaml` 里
`tasks.dialogue.temperature: 0.7`。

改完之后同一句「你觉得我能成功吗」：

> 能不能成功，我不知道，谁也不敢替你打包票。但有几件事是写在记录里的：2024 和 2025 连续两年智能车队校内赛，
> 你都拿了校级二等奖——同一个比赛隔一年还愿意回去打，这种人不多了。……
> 说实话，你现在问「能不能成功」，说明心里已经有一件想做的事了，只是还没说出口。
> 要不要今晚就写一句「我想做成……」，写完不用给任何人看？不想写也行。

## 2. 一次调用的完整路径

```
life ask "我好累"
  ↓
① 三路检索（见 [`检索.md`](检索.md)）→ 5~8 条旧记录 + 最近三天的记录
  ↓
② 按 §4.4 的顺序拼上下文，四块：
     底色摘要（core.md 压成最多 15 行）
     相关章节标题（只是标题，不带全文）
     三路召回的 entry（每条带**日期——优先用人话时间 when**、档位、锚点、卡点、原话、情绪）
     最近 3 天的 entry
  ↓
③ 估算上下文大小，超过 15k token 就一条条减少召回条数
  ↓
④ 调对话模型。system = life/prompts/ask.md（人设 + 禁止清单 + 三条硬要求）
  ↓
⑤ 校验回答，三条硬要求逐条查：
     有没有引用一个真实存在过的日期（认 2026-10-16 / 10-16 / 10月16日 几种写法）
     有没有踩禁止清单（空泛安慰 / 附和自我贬低 / 心理诊断 / 价值判断）
     有没有一次给三条以上建议
  ↓
⑥ 不合格 → 把「哪里没做到」回喂，重试一次
  ↓
⑦ 还不合格 → **单独**在回答下面显示「这次有硬要求没做到：…」，
     绝不拼进回答正文（踩过：拼进去之后，系统的自检提示看起来像 AI 说的话）
```

## 3. 关键代码在哪

```
life/ask.py::问()            主流程：召回 → 组装 → 调模型 → 校验 → 重试
life/ask.py::_组装上下文()    §4.4 规定的四块，顺序不能乱
life/ask.py::校验回答()      §4.4 验收的落地：日期 + 禁止清单 + 建议条数
life/ask.py::_提到了真实日期()  日期写法归一后比对
life/ask.py::估算token()     粗估就够了，用来守 15k 这条线
life/prompts/ask.md          人设、禁止清单、三条硬要求（改这里不用动代码）
life/cli.py::ask()           命令本身，含 --dry-run / --num / --no-vectors
```

## 4. 为什么这么设计

最容易被做错的决定是：**禁止清单写进 prompt 就够了吗？**

不够。写进 prompt 只是「请求」它别那么说，实测里模型照样会冒出「你已经很棒了」。所以现在的做法是**两层**：
1. prompt 里写清楚禁止清单（尽力而为）；
2. 代码里用正则**真的检查一遍**，不合格就回喂重试一次。

这和 §4.2 抽取那边「不许说『请输出 JSON』然后祈祷」是同一个思路：**能验证的东西就不要只靠请求。**

第二个决定：**为什么非要它引用真实日期？**
因为「一个具体的旧细节」是这个功能的全部价值。如果它说的是「你以前也做到过」，那就是一句废话——用户自己也知道「以前可能做到过」，他缺的是**具体的、带日期的证据**。所以这条要求是硬的：上下文里那些日期，输出里必须至少出现一个。做不到就重试。

第三个决定：**上下文压到 15k 以内。**
不是省钱，是因为超长上下文反而会让模型抓不住重点（§3.1：「长上下文不是记忆方案」）。所以宁可少召回两条，也要把上下文压紧。

## 5. 已知限制

- **速度取决于模型**。实测同一句「你觉得我是个什么样的人」：`deepseek-v4-pro` **36.5 秒**，`glm-5.3-flash` **13.6 秒**，质量都合格。默认配置用的是后者；想换回深思模型就改 `providers.yaml` 的 `tasks.dialogue`。
- 上下文里如果只有 `ts`（时间戳），模型会把**补记的历史当成今天**。所以上下文一律优先给人话时间 `when`。

- **上下文是拼出来的，不是「理解出来的」**：如果三路检索没捞到对的那条，模型再聪明也答不到点上。所以第 2 周的真实验收标准是「它能不能提起你忘掉的事」，而不是「回答得好不好听」。
- **温度调高了会更容易跑偏**：0.7 会让句子更活，也更容易多写一句。校验器只拦硬要求（日期/禁止句式/建议条数），拦不住「感觉对但其实是空话」。
- 校验只能查**表面**：它抓得住「你已经很棒了」，抓不住「换了个说法的空话」。禁止清单是黑名单，永远不完整。
- 「复述用户刚说的话」这条没有实现检查——机器很难判断什么算复述。
- 日期检查依赖上下文里有日期。如果召回的是空结果，这条检查会自动放过（没有日期可比）。
- 回答长度靠 prompt 约束（3~6 句 / 200 字），代码不强制截断。
- 没有多轮记忆：每次 `life ask` 都是独立的一问一答，上一轮说了什么它不记得。
