# 示例数据（life demo）

## 1. 这个功能对用户是什么

一条命令，把一份**虚构的半年记录**灌进你的 vault，让你立刻看到「攒了半年数据之后这个工具长什么样」。

为什么需要它：新用户第一眼看到的是空目录，什么功能都试不出来。而「它能不能提起我忘掉的事」这种事，要有历史数据才看得出来。

**它灌进来的是假数据**——一个在学后端的学生的半年，编的。所以它有一条自我保护的规矩：**vault 里已经有你写的记录了，它就拒绝动手。**

```powershell
life demo                 # 灌示例数据（vault 空的才行）
life demo --force         # 硬灌（会混进你的真实记录里，慎用）
```

## 2. 一次调用的完整路径

```
life demo
  ↓
① 检查 vault/now/ 里有没有 .md
     有 → 拒绝，并给出三个选择（换 LIFE_HOME / 加 --force / 直接记自己的）
     没有 → 继续
② 把 data.example/ 下所有文件按相对路径抄进 vault/
     （也就是 now/ chapters/ goals/ portrait/ core.md）
③ life reindex 重建索引（18 条记录、2 个章节、1 个目标、5 条底色）
④ 提示你可以试哪几条命令
```

`data.example/` 里有什么：

```
now/2026-09/… 2026-10/… 2026-11/…   18 条记录，跨 3 个月，带锚点和情绪
chapters/OAuth 调试.md               2 个章节
chapters/订单模块性能.md
goals/学完后端基础.md                1 个目标
core.md                              5 条底色
portrait/2026-Q3.md                 2 份画像（Q4 那份带 diff，含删除线）
portrait/2026-Q4.md
review-2026-Q4.html                 1 份季度回顾（单文件 HTML）
```

## 3. 关键代码在哪

```
life/cli.py::demo               命令本身（检查 → 复制 → 重建索引 → 提示）
life/config.py::示例数据目录()  固定指向仓库里的 data.example/（不看 LIFE_HOME）
data.example/README.md          这份假数据是什么、能用来干什么
```

## 4. 为什么这么设计

**① 为什么示例数据是静态文件，而不是脚本现生成？**
现生成要跑模型、要联网、要花钱，而且每次生成的内容都不一样——出问题没法复现。静态文件的好处是：**它本身就是「带锚点的压缩」的示范**，可以当抽取 prompt 的 few-shot 参考（设计 §13 明确说了这个用途）。

**② 为什么拒绝往有真实记录的 vault 里灌？**
这个产品的第一条硬约束是「vault 里是真人的真实人生记录」。假数据混进去，用户分不清哪条是真的，画像和回顾也会被污染。所以默认拒绝，`--force` 才放行——**默认值要给最不容易后悔的那个。**

**③ 为什么 `示例数据目录()` 不看 LIFE_HOME？**
`LIFE_HOME` 是「用户数据放哪」，示例数据是**代码仓库的一部分**。你把 LIFE_HOME 指到临时目录去试功能时，示例数据仍然应该找得到。第一版写成跟着 LIFE_HOME 走，实测直接报「找不到示例数据」——已修。

## 5. 已知限制

- 示例数据的时间是**写死的绝对日期**（2026-09 ~ 2026-11）。如果你是几个月后克隆的仓库，`life review --week` 会看不到它们（因为不在「最近 7 天」里）。
- 灌入后再跑 `life add`，新记录会和示例数据混在一起。想分开就用 `LIFE_HOME` 指另一个目录。
- `review-2026-Q4.html` 是**生成时就固化的**，不会跟着你的操作更新。
- 没有「清空示例数据」的命令，要清得自己删 vault/（或删具体文件）。
