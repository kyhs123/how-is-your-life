# 索引（SQLite 目录页）

## 1. 这个功能对用户是什么

半年后你会有几百条记录。想找「上次说很累是什么时候」，不能靠一个个翻文件。

索引就是这本书的**目录页**：让程序能在几秒钟内从几百条里挑出几条。但它有一个前提——**目录页撕了可以重印，正文永远在原处。**

所以 `life reindex` 的意义是：哪天索引坏了、你换电脑了、你手改了 markdown，跑一次就能从文件重新长出来一个完好的索引。

## 2. 一次调用的完整路径

```
life add 成功写出一条记录
  ↓
index.连接索引()   打开 vault/index.sqlite（不存在就建，顺便建表）
  ↓
index.写入条目()   同一个事务里干两件事：
                     entries      一行一条（id/ts/did/minutes/level/情绪/private…）
                     entries_fts  全文索引（did + 正文），同 id 先删再插
  ↓
（模型调用时）index.记录用量()  usage 表加一行：这次花了多少 token
```

重建的路径（`life reindex`）：

```
遍历 vault/now/**/*.md
  ↓
清空 entries 和 entries_fts（不是删库，是清表）
  ↓
逐个数：解析 front-matter → 写入索引
  ↓
读不动的文件跳过去，报出文件名，其它文件照常建好
  ↓
输出「扫描 N 个，成功 N 条」
```

## 3. 关键代码在哪

```
life/index.py::连接索引()   打开数据库并保证表存在
life/index.py::建表语句      三张表的 SQL，照 DESIGN.md §3.5 抄的
life/index.py::写入条目()   一条记录同时进 entries 和 entries_fts
life/index.py::重建索引()    life reindex 的实现
life/index.py::记录用量()    成本记账（token 数）
life/index.py::统计()        条目数、私有条数、待看条数、总 token
```

## 4. 为什么这么设计

最容易被做错的决定是：**能不能只存数据库、不存 markdown？**

能，而且更快、代码更少。但它被否掉了，因为那样会同时失去三件东西：

1. 你没法用记事本打开自己的记录；
2. 改一个字要用代码，不能直接改文件；
3. 数据库打不开的那天，你的人生记录就永久锁死了。

所以定了这条：**markdown 是真相源，SQLite 只是可重建的索引。** 索引丢了不算事故，`life reindex` 一分钟能补回来。这也是为什么 `*.sqlite` 在 `.gitignore` 里——它是可再生产物，不该进仓库。

第二个决定：全文索引用 SQLite 自带的 FTS5，而不是自己写搜索。因为中文不需要额外装分词库也能用 `trigram`（三个字一组切）模式，装起来零成本。

## 5. 已知限制

- `trigram` 分词要求**查询至少 3 个字**。搜「OAuth」可以，搜「累」这种单字搜不到。第 2 周做检索时会针对中文短词再补一层。
- 索引里还没有 `vec_entries`（向量表）和 `chapters`、`goals` 三张表，第 2、3 周才用得上，现在建了也是空的。
- `life reindex` 是**整体重建**，不是增量。几百条记录大概一两秒，几千条以后要改成增量。
- 索引里多存了一个 `body` 字段（正文），比设计文档的表结构多一列——因为全文检索要搜正文，不存就搜不到。
- 没有任何「谁在用这个索引」的锁。同时开两个终端跑 `life add` 极小概率互相卡住，现在没处理。
