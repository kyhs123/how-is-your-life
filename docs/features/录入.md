# 录入（life add）

## 1. 这个功能对用户是什么

你想记一句话的时候，敲一条命令就完事。它不会先问你「这属于哪一类」「打个几分」「目标是什么」——你只管说，剩下的它自己整理。

哪怕你在地铁上没网，这句话也**一定**存住了。回头联网再补，一个字都不会丢。

```
life add "今天把 OAuth 调通了，卡在 state 参数签名，调了 4 小时"
life add --image 截图.png "项目截图"
life add --emotion "今天很累，什么都不想做"
life add --private "这句只存本地"
```

## 2. 一次调用的完整路径

```
你敲 life add "…"
  ↓
① 检查输入：空的 → 提示用法；图片不存在 → 报错。任何一条不过就退出，什么都不写。
② 图片（如果有）复制进 vault/inbox/图片暂存/
③ 算指纹 = sha256(抹平空白后的原文 + 图片字节)
④ 指纹在缓存里，且对应文件还在 → 「这条之前记过了」，结束（幂等）
⑤ 写 vault/inbox/<id>.json   ←★ 到这一行执行完，这件事就已经不会丢了
⑥ 调模型抽取（--demo 时换成假模型；--private 时完全不调）
⑦ 结果写成 vault/now/2026-11/<id>.md（可能不止一个文件）
⑧ 同一份数据写进 SQLite 的 entries + entries_fts
⑨ 删掉 inbox 里那个 json（它的使命完成了）
⑩ 有图片：OCR 全文写进 vault/media/<id>.md，原图删掉（--keep-image 则保留）
⑪ 把「指纹 → 记录文件路径」写进缓存，下次重复提交能认出来
```

第 ⑤ 步之后任何一步失败，都会保留 inbox 里的 json，`life retry` 可以补抽。

## 3. 关键代码在哪

```
life/cli.py::add()              整条流程的控制者，每一步都在这里串起来
life/cli.py::_抽取并保存()      呼叫抽取、分配 id、写 markdown、写索引
life/cli.py::_处理图片()        图片的收尾（OCR 留下、原图删掉）
life/store.py::写inbox()        第一落盘
life/store.py::内容哈希()       算指纹，用于防重复
life/store.py::写条目()         把一条 entry 写成 markdown
life/extract.py::抽取()         调模型 / 假模型，返回干净的字段
```

## 4. 为什么这么设计

最容易被做错的决定是：**先抽取，还是先落盘？**

「先抽取再落盘」很自然：反正要调模型，拿到结果再写文件更省事。但它被否掉了：

- 断网时命令直接失败，用户写的东西**当场蒸发**；
- 模型超时 30 秒，用户以为没记上，又敲一遍，结果存了两条；
- 抽取结果不合要求时，原话已经不知道去哪了，没法重来。

所以顺序反过来：**先让「这件事发生过」变成硬盘上的事实，再谈加工。** 抽取失败只是「加工没成功」，不是「记录没成功」。这就是设计文档里 C5 那条硬约束的落地方式。

配套的另一个决定：抽取**在你眼前同步做完**（大约 2~5 秒），而不是偷偷开一个后台进程。慢一点，但每一步你都能看见，出错时屏幕上会直接说原因。

## 5. 已知限制

- 敲完要等 2~4 秒（实测调模型的时间）。断网时不会等，几秒后告诉你「存好了，但没抽成」。
- 一次只处理一条输入，不支持粘贴一整天的日记自动拆成多条。
- 重复判断看的是原文。同一件事换个说法再记一遍，会被当成两条——这是故意的，因为「补充细节」和「重复」机器分不清，宁多不少。
- 图片走的是多模态接口，已用一张终端截图实测通过（OCR 逐行抄全、原图删除、一张图拆成两条记录）。超长截图可能被 `max_tokens` 截断，没测过边界。
- `--private` 的记录不会被 AI 加工，只会把原话截断到 60 字存下来，状态标成 `needs_review`。
