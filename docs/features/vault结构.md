# vault 结构：你的记录存在哪、长什么样

## 1. 这个功能对用户是什么

你写下的每一条记录，最后都变成硬盘上一个**普普通通的文本文件**。用记事本就能打开，能复制、能备份、能拷到 U 盘、能用 git 看着它一行行变化。就算有一天这个程序跑不起来了，你的记录也一个都不会少——它们从来不属于这个程序，只属于你。

第一次运行任何命令时，程序会自己把文件夹和几个占位文件建出来，你不需要手动准备。

## 2. 一次调用的完整路径

### 2.1 `life add` 之后，vault 里多了什么

```
vault/
├── inbox/20261125-162438.json          ← 先落盘的原话（抽取成功后自动删）
├── now/2026-11/20261125-162438.md      ← 真正的记录，一个文件一条
├── 缓存/抽取/3f/3f9a…c1.json            ← 抽取结果缓存 + 防重复的凭据
├── media/20261125-162448.md             ← 文件的全文（传了文档/图片才有）
└── index.sqlite                         ← 索引，删了能用 reindex 重建
```

顺序是**固定的**，这是「断网也能记录」的全部秘密：

```
算指纹 → 查是不是重复提交
  ↓
写 inbox/<id>.json      ★ 这一行之后，内容就不会丢了
  ↓
调模型抽取（这一步可能失败、可能超时、可能断网）
  ↓
写 now/<月>/<id>.md
  ↓
建索引 → 删 inbox → 写缓存
```

抽取失败了，`inbox` 里那个 json 还在，`life retry` 或首页的「补抽」能接着做。记录本身不受影响。

### 2.2 一条记录长什么样

这是 `data.example/` 里的一条（虚构数据）：

```markdown
---
id: 20260901-184838
ts: 2026-09-01T18:48:38+08:00
when: ""
part: record
did: "照着教程跑通 Spring Boot 的 Hello World，理解不了自动配置从哪来"
minutes: 120
outcome: done
anchors:
  tech: ["Spring Boot"]
  people: []
  link: ""
emotion:
  valence: 0.1
  arousal: 0.6
  trigger: ""
  quote: ""
level: 1
goal: "学完后端基础"
chapter: ""
blockers: []
private: false
status: settled
---
照着教程跑通 Spring Boot 的 Hello World，理解不了自动配置从哪来
```

上面两行 `---` 夹住的那一段叫 **front-matter**（文件开头的键值表，YAML 格式），`---` 下面的才是正文。程序改记录时只碰上面那段，你手写在正文里的东西不会被它整理掉。

字段一个不落地说清楚：

| 字段 | 什么意思 | 例子 |
|---|---|---|
| `id` | 记录的唯一编号，**同时也是文件名** | `20260901-184838`（年月日-时分秒，北京时间） |
| `ts` | 程序用的时间戳，带时区 | `2026-09-01T18:48:38+08:00` |
| `when` | **给人看的时间**，可以啥也不写 | `大学期间`、`2023`、`大三上`、空 |
| `part` | 这条属于哪种 | `record` 做过的事 / `plan` 打算做的事 / `emotion` 一条感受 |
| `did` | 一句话说清做了什么（**不超过 60 字**） | 上面那行 |
| `minutes` | 花了多少分钟，不知道就 0 | `120` |
| `outcome` | 结果 | `done` 做完 / `stuck` 卡住 / `dropped` 放弃 |
| `anchors.tech` | 碰到的技术、工具、学科 | `["Spring Boot"]` |
| `anchors.people` | 涉及到的人（**只写你愿意写的**） | `["导师"]` |
| `anchors.link` | 相关的链接 | `""` |
| `emotion.valence` | 情绪正负，-1 到 1 | `0.1` |
| `emotion.arousal` | 情绪强弱，0 到 1 | `0.6` |
| `emotion.trigger` | 是什么引起的 | `""` |
| `emotion.quote` | 你当时说的原话 | `""` |
| `level` | 分层：1 做过 / 2 做成过 / 3 别人认可过 | `1` |
| `goal` | 挂在哪个人生目标下 | `学完后端基础` |
| `chapter` | 属于哪一段（章节） | `""` |
| `blockers` | 卡在哪 | `[]` |
| `private` | 只存本地：不被检索、不发给模型 | `false` |
| `status` | `pending` 待处理 / `settled` 已定稿 / `needs_review` 等你看一眼 | `settled` |
| 正文 | 你当时的原话（默认和 `did` 一样） | — |

**`ts` 和 `when` 为什么要有两个？** 因为「不记得哪天」太常见了。`ts` 是程序要的（排序、按月分文件夹、算「这周做了什么」），`when` 是给人看的（`大学期间` 比 `2023-09-01` 更接近你记得的样子）。补记过去的事时，`ts` 记的是**你补记的那一刻**，`when` 才写真实的时间——所以看记录的时候要认 `when`，不是认文件名。

### 2.3 每个文件夹管什么

| 路径 | 装什么 | 删了会怎样 |
|---|---|---|
| `inbox/` | 还没抽成的原始输入（json） | 那些输入就没了，记录的没影响 |
| `inbox/图片暂存/` | 图片在等 OCR，读完就删 | 没事（**不存原图**） |
| `now/YYYY-MM/` | **真正的记录，一条一个文件** | 记录就没了。这是要紧的东西 |
| `media/` | 文档/图片的全文（`<输入id>.md`）、你要求留下的原文件、`关联.json` | 全文没了，记录还在 |
| `缓存/抽取/<指纹两位>/<指纹>.json` | 抽取结果 + 防重复的凭据 | 记录不受影响；但「同一句话提交两遍」就认不出来了 |
| `chapters/*.md` | 章节（一段时期、一个方向） | 章节没了，记录还在 |
| `goals/*.md` | 人生目标 | 目标没了，记录还在（`goal` 字段变成对不上号） |
| `portrait/*.md` | 季度画像 | 能重新生成 |
| `core.md` | 底色：最多 50 条，只能靠证据晋升上来 | 很难重建，别删 |
| `corrections.md` | 你说的「不对，应该是这样」（还没做） | — |
| `changelog.md` | 每次提名、晋升、拒绝留一行 | 历史没了 |
| `index.sqlite` | 索引：搜索、按标签筛、按月统计都靠它 | **随便删**，`life reindex` 从 markdown 重新长出来 |

### 2.4 索引里有什么

`index.sqlite` 只有一张表是「正文」，其他都是目录页：

| 表 | 一行是什么 |
|---|---|
| `entries` | 一条记录（`did`、`body`、`anchors`、情绪、`status`… 都是 markdown 里的东西） |
| `entries_fts` | 全文检索用的倒排表（中文按三字一组切，`trigram`） |
| `chapters` / `goals` / `core` | 章节、目标、底色的目录页 |
| `vec_entries` | 向量（**现在是空的**：只用本机接口，没接 embedding） |
| `usage` | 每次调模型花了多少 token（给自己看的账本） |

`entries` 里存了一份 `body` 副本，这不是重复设计——检索要在正文里找字，SQLite 比「打开 500 个文件再搜」快得多。**真相仍然是 markdown**，索引随时可以推倒重来。

## 3. 关键代码在哪

```
life/store.py::确保vault就绪()        建目录、建占位文件；幂等（重复跑没事）
life/store.py::目录清单 / 占位文件     应该有哪些目录和文件，就这两个常量说了算
life/store.py::写inbox()              先落盘：vault/inbox/<id>.json
life/store.py::新建条目()             把模型给的字段补齐成一条完整记录（缺的填默认值）
life/store.py::格式化成markdown()     一条记录 → 那个带 --- 的文本（手写拼，不用 yaml.dump）
life/store.py::从markdown解析()       文本 → 一条记录；顺便查「文件名和 id 对不对得上」
life/store.py::分配id()               同一秒撞名就往后挪 1 秒
life/store.py::_原子写入()            先写 .tmp 再改名，断电不会留下半个文件
life/index.py::建表语句 / 重建索引()   索引的全部结构，以及从 markdown 重建的入口
life/recorder.py::记录一条()          上面那条时间线的总调度
```

## 4. 为什么这么设计

**① 为什么不直接存数据库？**

数据库更快、写代码更省事，但被否掉了：

1. **坏了就全丢。** 数据库打不开的时候，普通人没有任何办法把它读出来；纯文本坏了，你至少能看见哪一行不对、能手工救。
2. **没法看、没法比。** 半年后你想知道自己改过什么，纯文本能 `git diff` 一行行对上；数据库是二进制。
3. **被程序绑住。** 纯文本十年后还能打开，某个软件的数据库格式不一定。

所以这条规矩写死在 `docs/DESIGN.md`：**markdown 是真相源，SQLite 只是目录页。**

**② 为什么先写 `inbox`，而不是直接抽完再存？**

如果反过来，抽取失败 = 你说的话丢了。而「断网时仍然能记录」是 `AGENTS.md` 的硬约束之一。代价是抽取成功之后要多删一个文件——这个代价小得多。

**③ 为什么 `did` 限 60 字？**

一句话能看完的东西才会被回头看。原话不丢——它在正文里、在 `media/` 的全文里。压成 60 字是给**未来的你**省力气，不是给程序省空间。

**④ 为什么 `vault/` 写进 `.gitignore`？**

里面是真实的人生记录。一旦推到 GitHub，就算你立刻删掉，也可能已经被 fork、被缓存、被搜索引擎收录，**永久无法挽回**。所以它从第一天就不进 git。

## 5. 已知限制

- **整个 vault 没有加密。** 谁能打开这个文件夹，谁就能读你写的所有东西。要真正的保险柜，得靠 Windows 账户密码 / BitLocker 那一层。
- **私密记录（`private: true`）只是不发给模型、不被检索**，它在磁盘上和别的记录一样是明文。
- **`缓存/抽取/` 删了会丢「防重复」的历史**：同一句话再提交一次，会变成两条。
- **有几个目录名是中文**（`图片暂存`、`缓存`）。你自己的 Windows 上没问题，某些老旧的命令行工具处理中文路径会出错。
- **`chapters/`、`goals/`、`portrait/` 现在是空的**，等你真的开始用、开始晋升之后才会有内容。
- **`corrections.md` 还是占位文件**：你说的「不对，应该是这样」目前无处可写（见 `docs/决策记录.md` 的待定项）。
