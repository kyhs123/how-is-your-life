# vault 结构：你的记录存在哪

## 1. 这个功能对用户是什么

你写下的每一条记录，最后都变成硬盘上一个普普通通的文本文件。用记事本就能打开，能复制、能备份、能拷到 U 盘里。就算有一天这个程序跑不起来了，你的记录也一个都不会少——它们从来不属于这个程序，只属于你。

第一次运行任何命令时，程序会自己把这些文件夹和几个占位文件建出来，你不需要手动准备。

## 2. 一次调用的完整路径

任何命令（`add` / `retry` / `reindex`）开头都会先跑一遍「确保 vault 就绪」：

```
life add "..."
  ↓
store.确保vault就绪()
  ├─ 缺哪个目录就建哪个：inbox / inbox/图片暂存 / now / chapters / goals / portrait / media / 缓存
  ├─ 缺哪个占位文件就写哪个：core.md / corrections.md / changelog.md
  └─ 已经存在的一律不碰（所以你手改过的内容不会被覆盖）
  ↓
后续命令才开始干活
```

一次 `life add` 之后，vault 里会多出这些东西：

```
vault/
├── inbox/20261125-162438.json      ← 先落盘的原话（抽取成功后自动删）
├── now/2026-11/20261125-162438.md  ← 真正的记录，一个文件一条
├── 缓存/抽取/<指纹>.json            ← 抽取结果缓存 + 防重复的凭据
├── media/20261125-162448.md        ← 图片的 OCR 全文和摘要（图片才有）
└── index.sqlite                    ← 索引，删了能用 reindex 重建
```

## 3. 关键代码在哪

```
life/store.py::确保vault就绪()   建目录、建占位文件，幂等（重复跑没事）
life/store.py::目录清单          应该有哪些目录，就这一个列表说了算
life/store.py::占位文件          三个空文件的开头内容
life/store.py::_原子写入()       先写 .tmp 再改名，断电也不会留下半个文件
```

## 4. 为什么这么设计

最容易被做错的决定是：**要不要直接存数据库？**

数据库更快，写代码也省事，但被否掉了，有三个理由：

1. **坏了就全丢。** 数据库文件打不开的时候，普通人没有任何办法把它读出来。纯文本坏了，你至少能看见哪一行不对。
2. **没法看、没法比。** 半年后你想知道自己改过什么，纯文本可以用 `git diff` 一行行对上；数据库是一堆二进制。
3. **被程序绑住。** 纯文本十年后还能打开，某个软件的数据库格式不一定。

所以定了这条规矩：**markdown 是真相源，SQLite 只是目录页。** 索引随时可以删，`life reindex` 会从 markdown 重新长出来。

`vault/` 同时写进了 `.gitignore`：它永远不会被上传。这是故意的——里面是真实的人生记录。

## 5. 已知限制

- 有几个目录名是中文（`图片暂存`、`缓存`）。在你自己的 Windows 上没问题，但某些老旧的命令行工具处理中文路径会出错。
- 第 1 周只用到 `inbox`、`now`、`media`、`缓存` 四个目录；`chapters`、`goals`、`portrait` 现在是空的，第 3、4 周才会往里写东西。
- `data.example/`（能一键生成假数据的演示集）还没做，那是第 4 周的事。
