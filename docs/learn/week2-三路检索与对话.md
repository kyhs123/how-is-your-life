# 第 2 周：三路检索与对话

## 1. 这周做了什么

让程序能听懂一句人话，从我半年的记录里翻出我自己忘掉的事，然后照着证据回答我，而不是说空话。

## 2. 这些知识在真实世界里用在哪

**场景一：几乎所有「搜索」都是多路混合。** 你在淘宝搜「红色连衣裙」，它同时在跑关键词匹配、向量相似、销量和时间的规则——一路检索永远不够。这周写的就是这个骨架的最小版。

**场景二：所有接大模型的产品都在做同一件事——RAG（先检索、再让模型照着检索结果说话）。** 企业知识库、客服机器人、代码助手，全都卡在同一个问题上：把哪几段资料塞进上下文。塞错了，模型就开始编。这周学的「三路召回 + 上下文限额 + 输出校验」，换个业务直接能用。

## 3. 出现的名词，大白话解释

| 术语 | 一句话解释 | 在本项目里指什么 |
|---|---|---|
| embedding（向量） | 把一段文字变成一串数字，意思相近的数字也相近 | 用来实现「按意思搜」 |
| 余弦相似度 | 两个向量「方向」有多接近，1 = 完全同向 | 判断两条记录意思像不像 |
| FTS5 | SQLite 自带的全文检索引擎 | 按关键词找记录 |
| trigram | 把文字切成三个字一组来建索引 | 中文不用装分词库也能搜 |
| RRF | 按「第几名」给分，不按「多少分」，把多路结果合起来 | 两路都命中的记录排最前 |
| rerank（精排） | 粗筛之后再用一个模型重新排一遍 | 暂时没用（没接口） |
| 上下文 | 模型一次能同时看到的全部内容 | 拼给对话模型的那几块材料 |
| 幻觉 | 模型编出不存在的事，还说得像真的 | 所以要求它「没有就说没有」 |
| SQL 直达 | 不靠文字匹配，直接用条件查数据库 | 「给我所有情绪 < -0.5 的记录」 |

## 4. 三个「为什么这么设计」

**① 为什么是三路，而不是把记录全塞给大模型让它自己挑？**
否掉的方案：一次对话把半年的记录都塞进去。理由三条——塞不下（§3.1 明说永远不要全塞）、一次几万 token 成本立刻失控、而且模型**没有时间感**，你不知道它凭什么挑了那几条。三路各管一件事：向量管「意思像」，全文管「特定的词」，SQL 管「时间和情绪」。

**② 为什么把禁止清单写成代码检查，而不是只写在 prompt 里？**
因为写进 prompt 只是「请求」它别那么说。实测里它照样会冒出「你已经很棒了」。所以现在 prompt 里写一遍、代码里用正则**再查一遍**，不合格就回喂重试。能验证的东西，就不要只靠请求。

**③ 为什么非要它引用真实日期？**
否掉的方案：让它自然地说「你以前也做到过」。但那是废话——我自己也知道「以前可能做到过」，我缺的是**具体的、带日期的证据**。所以这条是硬要求：上下文里那些日期，回答里必须出现一个。做不到就重试。

## 5. 你可以自己动手试的一件事

```powershell
# 只看它翻出了什么，不花钱调对话模型
.\.venv\Scripts\life.exe ask "OAuth" --dry-run
.\.venv\Scripts\life.exe ask "导师" --dry-run
.\.venv\Scripts\life.exe ask "我好累" --dry-run
```

三次输出的「三路命中」会完全不一样：`OAuth` 主要走全文路，`导师` 走实体匹配，`我好累` 一条文字都不命中、只走结构路（SQL 的情绪条件）。**这就是三路存在的理由**——同一句话，靠文字匹配根本找不到的东西，靠 SQL 找到了。

## 6. 面试官问起这周的东西，你可以这么答

**S**：做一个本地人生记录工具，第二周要做的是「从自己的旧记录里找回忘掉的事」。

**T**：难点是人的提问方式和记录的文字根本不重合——我说「我好累」，记录里写的是「面试前失眠」。

**A**：我做了三路混合检索（向量找意思、全文找关键词、SQL 按时间和情绪找），用 RRF 按名次融合；再把结果按固定结构拼进上下文，并且**用代码校验模型输出**——必须引用一条真实带日期的旧记录，不许出现空泛安慰。

**R**：实测问「我好累」，它翻出了 40 天前的崩溃记录和 3 天前的跑步记录，回答里带了两个真实日期；问一件记录里没有的事，它直接说「你记录里没有，我不编」。
