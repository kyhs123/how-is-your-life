# 第 3 周：目标与晋升

## 1. 这周做了什么

让一堆散着的记录自己长出「主线」——但它只会提名，**要不要认这条线，永远由我说了算**。

## 2. 这些知识在真实世界里用在哪

**场景一：所有「自动归纳 + 人工确认」的系统。** 手机相册自动把人脸聚成一组、邮件自动分成「工作/订阅」、代码扫描自动标出可疑位置——工业界的通行做法都是「机器先提，人再点确认」。为什么？因为机器错一次，用户就再也不看它的建议了。

**场景二：任何要给数据分层的系统。** 新闻 App 把 1000 条新闻分成 10 个专题、电商把商品分成类目——都得先决定「哪些算同一类」，再决定「够不够格升级成一个正式类目」。这周写的就是这套判断条件的最小版。

## 3. 出现的名词，大白话解释

| 术语 | 一句话解释 | 在本项目里指什么 |
|---|---|---|
| 当下 / 章节 / 底色 | 三个时间尺度：这周的、这半年的、这辈子的 | 三层记录结构 |
| 晋升 | 从短的一层升到长的一层 | 散记录 → 章节 → 底色 |
| 提名 | 机器说「这条够格了」，但还不算数 | `life settle` 的产物 |
| 固化 | 把零散记录归纳成阶段主题 | `settle` 干的事 |
| 证据档位 | 接触 / 复现 / 产出 / 能讲，四档 | 判断「学过」还是「会」 |
| 回连 | 用关键词把历史里的同类记录也找出来 | 只看一周永远凑不出「跨两个月」 |
| 幂等 | 同一件事做两遍，结果不变 | 拒绝的提名不再重复提 |

## 4. 三个「为什么这么设计」

**① 为什么不让系统自动晋升？**
否掉的方案：模型判断「这条是主线」，直接建章节。理由：**错判一次用户就不再信任系统**。「我以为你重视这个」经常是错的——你可能只是在应付作业。所以固定成「系统提名 → 你确认」。

**② 为什么不显示完成百分比？**
否掉的方案：目标卡片上写「62%」。三个理由：进度不是线性的（一个月没动静很正常）；百分比要人手动填，一填就变成打卡（这类项目头号死因）；百分比不给证据——「62%」不能拿去面试，「给同学讲了 JWT 刷新」可以。

**③ 为什么 settle 只看一周，条件却要看全库？**
这是设计文档两处对不上的地方：§4.6 说每周读本周记录，§3.2 却要求「跨 ≥2 个月」才够格。只看一周永远凑不出来。解法是分工：**本周记录用来发现主题，主题里的关键词用来把历史记录串起来**，条件跑在串完的全量上。

## 5. 你可以自己动手试的一件事

```powershell
.\.venv\Scripts\life.exe goal add "学完后端基础" --horizon term --why "想自己能做一个网站"
.\.venv\Scripts\life.exe goal show 1
```

看输出里有没有一个 `%`。**没有就对了**——这个产品的设计原则之一，就是不用百分比衡量人生。

如果你已经记了几天，再跑 `life settle --week`，看它给你提了哪条线，以及「依据」那行是不是真的对得上你的记录。

## 6. 面试官问起这周的东西，你可以这么答

**S**：做一个记录工具，第三周要做的是让散落的记录自己长出「主线」。

**T**：难点是判断「哪些记录属于同一件事」，以及「够不够格升级」——但机器一旦判断错了，用户就再也不信它。

**A**：我用模型做**提名**、用代码做**条件校验**（跨月份、有产出物、至少三条），流程固定成「系统提名 → 用户确认」；同时解决了一个设计上的坑：只看本周记录永远凑不出「跨两个月」，所以用主题关键词把历史记录回连进来再判条件。

**R**：实测四条跨三个月的 OAuth 记录被正确串成一条主线，晋升后四个文件的 `chapter` 字段全部回填，`changelog.md` 留下了「提名」和「晋升」两行可追溯的记录。测试 76 个，全部只从命令行验证用户能看到的结果。
