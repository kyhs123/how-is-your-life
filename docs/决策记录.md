## 一、已确认

### 1. 抽取的时机：先落盘，再在同一个命令里抽完（2026-11-25）

**定了什么**
`life add` 先把原话写进 `vault/inbox/<id>.json` 并落盘，然后**在同一个命令里**调模型抽取；抽完才返回。不加后台进程。

**为什么**
设计 §4.1 写的是「后台队列异步抽取」，但这是个命令行工具，没有常驻服务。两条路里选了简单的那条：

- 同步抽完再返回 → 慢 2~4 秒，但每一步你都看得见，出错直接报在屏幕上
- 偷偷起一个后台子进程 → 感觉快，但它失败时屏幕上什么都不显示，Windows 上极难查

**代价**
`life add` 要等 2~4 秒。断网时不等，几秒后告诉你「存好了，但没抽成」，用 `life retry` 补。

**已写入 DESIGN.md（2026-11-25）**
位置：§4.1 流程末尾的「实现说明」。原文的「后台队列」没有删，只是注明这一版怎么落地的。

### 2. 可视化：一个单文件静态网页 `life board`（2026-11-25）

**定了什么**
`life board` 把 `vault/` 里的记录渲染成一个自包含的 HTML（`vault/看板.html`），双击用浏览器打开。CSS 内联、图表用 Python 算坐标后手写 SVG、没有任何外链、不引入前端框架、不起服务。

**为什么**
设计 §11 明写「不做前端框架 / 服务端」，§4.8 又留了一个口子：「可选生成单文件 HTML，双击可看，不引入前端框架」。所以不是新开一个形态，而是把 §4.8 的展示部分**提前**了。

**代价**
- 只有「看」：不能改、不能搜、不能按月份筛选
- §4.8 要的「证据分布变化」「晋升事件」「下周建议」没有——要等第 3、4 周
- 样式改起来比框架土

**已写入 DESIGN.md（2026-11-25）**
位置：§4.8 末尾的「实现说明」＋ §10 路线图第 1 周那行。§4.8 原本要求的「变化 / 晋升事件 / 建议」明确留在第 4 周。

### 3. 网页编辑：先不做，CLI 先走，编辑界面排第 5 周（2026-11-25）

**定了什么**
网页看板保持**只读**。目标先按设计做命令行版（第 3 周：`life goal add <id>/list/done/stop`）。**能编辑的网页界面排到第 5 周**，当独立一周做。

第 5 周第一版只做两件事：
1. 新建 / 修改目标
2. 把 `needs_review` 的记录勾成 `settled`

**为什么**
1. 设计 §11 明确「MVP 只要 CLI」。做可写网页必须有一个接收写请求的东西——那就是服务端，属于改设计。
2. 设计 §10 说得非常重：第 2 周（检索 + `life ask`）是整个项目的验证点。「如果它提不起你忘掉的事，后面全是空的。」在验证产品价值之前先做编辑 UI，是把力气花在错的地方。
3. 写操作直接改用户的人生数据。只读页面出错最多难看，可写页面出错会把记录改坏。

**代价**
你要再等两周多才能在网页上点点点；在那之前「编辑」靠手改 markdown。

**第 5 周开工前必须先读的坑**
设计 §4.5 对目标有明确禁止清单：**不替用户定目标、不催进度、不发提醒、不做 KPI 面板、不标红未完成、不连续天数。** 做编辑界面时最容易顺手加「进度条」「连续记录 N 天」，那正是这个产品要避免的。这条要写进那一周功能文档的验收项。

**已写入 DESIGN.md（2026-11-25）**
位置：§10 路线图新增第 5 周 + 变更说明、§10.2（从「MVP 之后」清单里移走「Web 界面」）、§11 加了例外条款。

### 4. 只用一个本机接口，不接任何外部付费服务（2026-11-25）

**定了什么**
项目所有者明确：**没有预算，只用已有的那个本机接口**（`http://127.0.0.1:8788/v1`），不新接任何第三方服务。

因此 `providers.yaml` 里的 `tasks.embed`（向量）和 `tasks.rerank`（精排）两段**故意留空并加了注释**，`.venv` 里也不需要 `VEC_API_KEY`。

**这对检索的影响**
`life ask` 实际跑**两路**：全文 + 结构。向量路会自动跳过，并在命令行明说原因（不静默降级）。

**为什么不能用 chat 模型凑出向量**
把文字变成向量需要专门的 embedding 模型。chat 模型能吐数字，但那些数字没有「意思相近则相近」的性质，拿来算余弦等于随机排序——比明说缺一路更糟，因为看起来在工作、实际在乱给结果。也考虑过用「字重合度」冒充，同样被否：那是模糊文本匹配，不是语义，不该叫向量路。

**代价**
「按意思找」这个能力缺失。记录少时几乎无感；记录上到两三百条以后，当提问用词和记录用词完全不重合时会明显（比如问「我心里堵得慌」，记录写的是「面试前失眠」）。结构路（按情绪值和时间查）能兜住一部分，但兜不住全部。

**哪天有预算了**
在 `providers.yaml` 取消 `embed` / `rerank` 两段的注释、填上 key，跑一次 `life reindex --vectors` 就自动生效，**不用改一行代码**。
