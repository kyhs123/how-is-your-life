## 一、已确认

### 1. 抽取的时机：先落盘，再在同一个命令里抽完（2026-11-25）

**定了什么**
`life add` 先把原话写进 `vault/inbox/<id>.json` 并落盘，然后**在同一个命令里**调模型抽取；抽完才返回。不加后台进程。

**为什么**
设计 §4.1 写的是「后台队列异步抽取」，但这是个命令行工具，没有常驻服务。两条路里选了简单的那条：

- 同步抽完再返回 → 慢 2~4 秒，但每一步你都看得见，出错直接报在屏幕上
- 偷偷起一个后台子进程 → 感觉快，但它失败时屏幕上什么都不显示，Windows 上极难查

**代价**
`life add` 要等 2~4 秒。断网时不等，几秒后告诉你「存好了，但没抽成」，用 `life retry` 补。

**已写入 DESIGN.md（2026-11-25）**
位置：§4.1 流程末尾的「实现说明」。原文的「后台队列」没有删，只是注明这一版怎么落地的。

### 2. 可视化：一个单文件静态网页 `life board`（2026-11-25）

**定了什么**
`life board` 把 `vault/` 里的记录渲染成一个自包含的 HTML（`vault/看板.html`），双击用浏览器打开。CSS 内联、图表用 Python 算坐标后手写 SVG、没有任何外链、不引入前端框架、不起服务。

**为什么**
设计 §11 明写「不做前端框架 / 服务端」，§4.8 又留了一个口子：「可选生成单文件 HTML，双击可看，不引入前端框架」。所以不是新开一个形态，而是把 §4.8 的展示部分**提前**了。

**代价**
- 只有「看」：不能改、不能搜、不能按月份筛选
- §4.8 要的「证据分布变化」「晋升事件」「下周建议」没有——要等第 3、4 周
- 样式改起来比框架土

**已写入 DESIGN.md（2026-11-25）**
位置：§4.8 末尾的「实现说明」＋ §10 路线图第 1 周那行。§4.8 原本要求的「变化 / 晋升事件 / 建议」明确留在第 4 周。

### 3. 网页编辑：先不做，CLI 先走，编辑界面排第 5 周（2026-11-25）

**定了什么**
网页看板保持**只读**。目标先按设计做命令行版（第 3 周：`life goal add <id>/list/done/stop`）。**能编辑的网页界面排到第 5 周**，当独立一周做。

第 5 周第一版只做两件事：
1. 新建 / 修改目标
2. 把 `needs_review` 的记录勾成 `settled`

**为什么**
1. 设计 §11 明确「MVP 只要 CLI」。做可写网页必须有一个接收写请求的东西——那就是服务端，属于改设计。
2. 设计 §10 说得非常重：第 2 周（检索 + `life ask`）是整个项目的验证点。「如果它提不起你忘掉的事，后面全是空的。」在验证产品价值之前先做编辑 UI，是把力气花在错的地方。
3. 写操作直接改用户的人生数据。只读页面出错最多难看，可写页面出错会把记录改坏。

**代价**
你要再等两周多才能在网页上点点点；在那之前「编辑」靠手改 markdown。

**第 5 周开工前必须先读的坑**
设计 §4.5 对目标有明确禁止清单：**不替用户定目标、不催进度、不发提醒、不做 KPI 面板、不标红未完成、不连续天数。** 做编辑界面时最容易顺手加「进度条」「连续记录 N 天」，那正是这个产品要避免的。这条要写进那一周功能文档的验收项。

**已写入 DESIGN.md（2026-11-25）**
位置：§10 路线图新增第 5 周 + 变更说明、§10.2（从「MVP 之后」清单里移走「Web 界面」）、§11 加了例外条款。

**已实现（2026-11-25）**
`life server`，代码在 `life/server.py`，说明见 `docs/features/网页编辑.md`。

实现时又定了三件小事（都写进那份文档了）：

1. **用标准库 `http.server`，不引 Flask/FastAPI**。只有三个动作，不值得为此背一套框架的概念和依赖。
2. **加了三道校验**：`Host` 头（防 DNS rebinding）、一次性令牌 + `Origin`（防 CSRF）、所有输出转义。本地工具也不能省——浏览器里任何一个网页都能向 `127.0.0.1` 发请求。
3. **POST 一律 303 跳转**（PRG），否则刷新会重复提交，目标被建两遍。

实测踩到的坑：`secrets.compare_digest` 不支持含中文的字符串（会抛 TypeError、连接直接断），改成比较 UTF-8 字节。

**范围扩大（2026-11-25，同一天）**
第一版只做「改目标 + 确认记录」，验收时项目所有者指出：**「记录人生才是主要任务」**——页面不能记一条，就只是个配置面板。于是重写成完整的本机界面（记一条 / 记录列表 / 单条编辑 / 提问 / 目标 / 章节 / 画像 / 回顾 / 设置），并单独写了施工图 `docs/WEBUI.md`（先定文档，再按文档实现）。

同时明确的边界：**在页面里跑 `settle`/`portrait`/`review` 不现实**——它们要调模型 30 秒~2 分钟，同步表单提交会让人以为卡死。页面上只读展示结果 + 给出可复制的命令。

### 4. 只用一个本机接口，不接任何外部付费服务（2026-11-25）

**定了什么**
项目所有者明确：**没有预算，只用已有的那个本机接口**（`http://127.0.0.1:8788/v1`），不新接任何第三方服务。

因此 `providers.yaml` 里的 `tasks.embed`（向量）和 `tasks.rerank`（精排）两段**故意留空并加了注释**，`.venv` 里也不需要 `VEC_API_KEY`。

**这对检索的影响**
`life ask` 实际跑**两路**：全文 + 结构。向量路会自动跳过，并在命令行明说原因（不静默降级）。

**为什么不能用 chat 模型凑出向量**
把文字变成向量需要专门的 embedding 模型。chat 模型能吐数字，但那些数字没有「意思相近则相近」的性质，拿来算余弦等于随机排序——比明说缺一路更糟，因为看起来在工作、实际在乱给结果。也考虑过用「字重合度」冒充，同样被否：那是模糊文本匹配，不是语义，不该叫向量路。

**代价**
「按意思找」这个能力缺失。记录少时几乎无感；记录上到两三百条以后，当提问用词和记录用词完全不重合时会明显（比如问「我心里堵得慌」，记录写的是「面试前失眠」）。结构路（按情绪值和时间查）能兜住一部分，但兜不住全部。

**哪天有预算了**
在 `providers.yaml` 取消 `embed` / `rerank` 两段的注释、填上 key，跑一次 `life reindex --vectors` 就自动生效，**不用改一行代码**。

### 5. settle 只看本周，晋升条件却要跨月——两节对不上（2026-11-25）

**矛盾在哪**
- §4.6：`life settle --week` **每周跑一次，读本周全部 entry** → 识别主题 → 满足 §3.2 条件就提名。
- §3.2：「当下 → 章节」的第一条是**同一主题在 ≥2 个不同月份出现**。

只看一周的记录，永远不可能跨两个月。按字面实现，这个功能永远提不了名。

**怎么解的**
分工：**本周记录用来「发现」主题，主题里的关键词用来把「历史记录」串起来**，条件检查跑在串完之后的全部记录上。

具体做法：`life/prompts/settle.md` 要求模型除了标题和涉及条目，再给 2~4 个 `keywords`（技术名、项目名、卡点原文）；`promote._回连()` 用这些词在**全库**里搜同类记录，并进关联集。

**为什么不是另外两种解法**
- 「把 settle 改成读全部记录」→ 记录多了以后一次几十万 token，且违背 §4.6「每周跑一次」的原意。
- 「放宽条件，不要求跨月」→ 直接违背 §3.2，晋升就失去意义了（一周的兴致不能算主线）。

**代价**
回连靠关键词字面命中，可能漏（同义词对不上）也可能多（一个泛词串进无关记录）。所以条件里的「厚度 ≥3 条」同时起了防误伤的作用。

**要不要写进 DESIGN.md**
待定。建议在 §4.6 补一句：「条件检查基于主题回连后的全部历史记录，不只是本周那几条。」

### 6. 示例数据用静态文件 + `life demo`，不用脚本现生成（2026-11-25）

**定了什么**
`data.example/` 里放**静态的 markdown 文件**（18 条 entry、2 个章节、1 个目标、5 条底色、2 份画像、1 份回顾 HTML），`life demo` 把它们按相对路径抄进 `vault/` 再重建索引。

**为什么不用脚本现生成**
现生成要跑模型、要联网、要花钱，而且每次内容都不一样——出问题没法复现。静态文件还有个额外好处：**它本身就是「带锚点的压缩」的示范**，可以当抽取 prompt 的 few-shot 参考（§13 本来就是这个用意）。

**安全阀**
`vault/now/` 里已经有 `.md` 时，`life demo` **拒绝执行**，除非加 `--force`。理由：假数据混进真实记录里，用户就分不清哪条是真的，画像和回顾也会被污染。默认值要给最不容易后悔的那个。

**`make demo` 的偏差**
设计里写的是 `make demo`。Windows 上通常没装 make，所以实现成 `life demo`（跨平台），README 里写的就是它。

**实测踩到的坑（换模型时还会再踩）**
`life portrait` 第一版写出来的文件是**空的**。原因：这些模型是「思考型」，`max_tokens: 2000` 全被 reasoning 吃掉了（实测思考 3193 token、正文 0 字、`finish_reason=length`）。修法：`max_tokens` 和 `timeout` 都做成**按任务可配**，并且这种情况报错说人话，不再留空文件。

### 7. 「补记过去」不是一个模块，是「记一条」的一个字段（2026-11-25）

**我错在哪**
第一版把它做成了独立页面 `/import` + 独立命令 `life import`，还**强制填日期**（只填到月就按 1 号记）。

项目所有者当场指出两件事：

1. **「这个项目就是为了记录人生，那之前的人生怎么就不是人生？」**——把它做成独立入口，等于暗示「现在记的」和「以前发生的」是两种东西。这是概念错误。
2. **「不需要知道具体日期，只需要知道你做过这个、你会做这个就行了」**——简历要的是能力和证据，不是时间戳。

**改成什么**
「记一条」多一个**可选**字段 `when`：

| 填的 | 时间戳 | when | 显示 |
|---|---|---|---|
| 不填 | 现在 | `""` | 今天 |
| `2023-09` | 2023-09-01 12:00 | `2023-09` | `2023-09` + 说明补了 1 号 |
| `大一` | **录入时刻** | `大一` | `大一` + 「时间不详」 |
| 未来 | — | — | 拒绝 |

- 独立页面 `/import` 与 `life import` **已删除**，能力并入「今天」页和 `life add --when`
- `entry` 新增字段 `when`（已在 `DESIGN.md` §3.4 记录）；索引加同名列表，旧库自动补列
- 补记的旧记录默认进不了 `settle` 的 7 天窗口，所以给了 `life settle --since 2023-01`

**为什么不加 `date_precision`**
一开始想过加一个「精度」枚举（day/month/year/unknown）。后来用 `when` 一个字符串就够：
`when` 里本来就写着到底是 `2023` 还是 `2023-09-15`，人一眼能看出来，程序要精度时也能 parse。少一个字段少一处不一致。

**和简历的关系**
`DESIGN.md` §10.2 的「面试模式：从底色生成 STAR 卡」要靠这些记录挑素材。
**素材越全越好，日期越准越好，但不准也必须能记**——所以 `when` 只能是可选字段，不能是必填门槛。

### 8. 上传 .docx 会 400：三个真 bug 串在一起（2026-11-25）

**现象**
用户上传一份简历 `.docx`，页面报 `已存好，但抽取没成功（模型接口返回了错误（HTTP 400）） upstream 400 ... {"code":11135,"msg":"Please start a new conversation, replace the image, and try again."}`

**三个 bug，一个盖着一个**

1. **文档被当成了图片。** `recorder.抽取并保存` 里只要 inbox 里有文件就传给视觉模型——于是 `.docx` 的字节被 base64 成 `data:image/docx` 发过去，上游当然报「replace the image」。
   修：只有 `kind == "image"` 才走视觉通道。`life retry` 那条路径也有同样的问题，一起修了。
2. **上游 400 时我没降级。** 原来的降级只在报错文字里含 `response_format` 时才往下试；上游把错误包了一层，看不出原因，于是直接放弃。
   修：**400/422 一律先降一级再试**（三级降级的本意就是「不知道原因也往下试」）。
3. **思考型模型把额度花光。** 简历文本长，`max_tokens: 2000` 全被推理吃掉，正文 0 字（`finish_reason=length`）。
   修：`max_tokens` 配到 6000，并且代码在遇到「正文空 + length」时**自动翻倍重试一次**（上限 20000）；`timeout` 也配到 240 秒。超时报错也改成说人话（不再一律说「连不上」）。

**教训**
三个 bug 里，只有第 1 个是我设计失误（把「有文件」等同于「是图片」）；第 2、3 个是**降级策略写得太窄**。
「三级降级」不是一句口号——判断条件写得越窄，降级就越等于没有。

**顺带**
抽出来的 9 条 / 20 条两批重复了（崩在中途时防重复缓存没写）。已删掉旧的一批，现在 27 条无重复。
这也说明**「先落盘 + 可重试」是有代价的**：重试可能产生重复，需要缓存配合。已记在已知限制里。

### 9. 长任务从「回命令行」改成「后台任务 + 自刷」（2026-11-25）

**原来怎么定的**
第 5 周把 `portrait` / `review` / `settle` 挡在页面外，理由写得很明确：同步 HTTP 等一两分钟，浏览器像卡死，也容易超时。

**为什么改**
项目所有者看到画像页写着「回命令行跑 life portrait」，直接说：**「我希望主要的功能都能在可视化页面上点个按钮执行。」**
这个要求是对的——一个界面把最常做的事推回命令行，就不叫界面。

**怎么改的**
不是硬等，而是**后台任务**：

- 点按钮 → `POST /jobs/<动作>` → 起一个后台线程 → 立刻 303 到 `/jobs/<id>`
- 任务页用 `<meta http-equiv="refresh" content="3">` 每 3 秒自刷（**不加 JS**）
- 跑完显示结果 + 「去看看」的链接；失败显示原因 + 「重试」
- 任务表放内存，同类任务只允许一个（防重复烧 token）
- **不做进度条**：模型调用没有可靠进度回调，编百分比比转圈更糟，只显示「已经跑了多少秒」

**顺带补的一个真 bug**
`Location` 响应头只能是 latin-1，中文 id（任务名/目标名）会直接 500。已统一做百分号编码。

**代价**
任务表在内存里，重启就没了；也不可能做「跑到一半取消」。这两条都写进已知限制了。

### 10. 缓存分桶 + 瘦身；孤儿判定必须保守（2026-11-25）

**起因**
项目所有者问：「用久了会不会出现一堆文件夹？」——会，而且有一处真的会炸：抽取缓存是「每条内容一个 json」，五年九千个文件全堆在 `缓存/抽取/` 一层。

**做了两件事**

1. **缓存分桶**：`缓存/抽取/<指纹前两位>/<指纹>.json`，256 个桶，单目录最多几十个。老文件不用手动迁移——读到就顺手搬进桶。
2. **瘦身** `life tidy`（网页设置页也有按钮）：清 90 天前的缓存 + 确认没人引用的 media 全文 + 空目录。默认先干跑看数字，**记录一条都不动**。

**踩到的坑（差一点删掉数据）**
第一版孤儿判定按「文件名 = 记录 id」比对，结果把简历的两份全文判成了孤儿。真正原因是**media 用「输入 id」命名，记录用「记录 id」**——一条输入可能拆成多条记录，两套 id 对不上。

改成：新增 `vault/media/关联.json` 记录「哪个全文属于哪些记录」，只删「登记过、且那些记录一个都不在了」的文件；**没登记的一律不动**，只在报告里说「有 N 个分不清归属」。
宁可留几个垃圾，也不要删掉一张截图唯一的 OCR 全文。

**顺带修的一个低级错误**
改这些文件时脚本变量写错，把 `recorder.py` 的内容覆盖进了 `store.py`。`git checkout` 恢复后重做——记录一条没丢（因为都在磁盘上，跟代码无关）。

### 11. 三个问题：太慢、答得不对、测试数据污染（2026-11-25）

**用户一次问了三个**

1. 「回答得太慢，生成画像也慢」
2. 「这回答的是什么东西？我给了简历，为什么不基于简历回答」
3. 「是你测试时给的信息干扰了吗」

**查出来的三件事**

1. **慢 = 模型选得重。** 实测同一句提问：`deepseek-v4-pro` **36.5 秒**，`glm-5.3-flash` **8.6~13.6 秒**，质量都合格。画像 35 秒 → **9.6 秒**。
   决定：`dialogue` 与 `settle` 默认换成 `glm-5.3-flash`（它的推理开销只要 23 token，pro 要 400）。想换回来改 `providers.yaml` 一行。
2. **答不对 = 检索缺一路。** 「你觉得我是个什么样的人」这类元问题，字面上跟任何记录都不像，实测**三路全 0 命中**，只能退回「最近 3 条」——于是抓到的是噪音条和多智能体记录。
   决定：结构路里加一条**「代表性」检索**——问「我是什么样的人 / 我做过什么 / 我擅长什么」时，按档位降序挑 12 条，而不是按字面相似。
3. **确实有我的污染。** 那 6 条 OAuth / 订单模块 / 很累 / 导师 / JWT / 只存本地 都是**我演示时写的**；另外「这是我的简历…你记录一下」是上传时那句说明被单独记成的噪音条。
   决定：挪到 `vault/.归档-演示数据/`（不删、不进索引，想恢复随时能拿回来）；噪音条一起挪走。

**顺带修的一个真 bug**
简历那 20 条的 `when` 是空的、时间戳都是「今天」，而**上下文里给模型看的是时间戳**——所以模型说「你的记录里全是 2026-11-25 这一天」。
修：① 20 条标成 `when: 大学期间`；② 上下文和列表一律优先显示 `when`。

**修改后的实测**
- 提问：36.5 秒 → **13.6 秒**，答案开始引用「2024、2025 连续两年智能车队」「执导微电影」「焊 PCB 调机械臂」
- 画像：35 秒 → **9.6 秒**

### 12. 回答太生硬：把「不哄人」和「像台账」分开（2026-11-25）

**反馈**：「我觉得回答太生硬了，能不能加一些提示词让他回答的更温情一点，也更有指导价值一点，给出一些有用的建议，像老师、像父亲、像朋友，但不能瞎说，要基于现实。」

**问题在哪**
设计 §7.2 的禁止清单（不许「你已经很棒了」「相信自己」「加油」）我在 prompt 里写得非常硬，结果模型为了「安全」，
退化成了念证据：「2026-11-25 你调 OAuth 卡在 state 参数签名…同一天你把订单模块…」——**它没说错，但它不像人说话**。

**改了三处**
1. **人设**：从「不是安慰者」改成「既了解他、又不哄他的长辈：老师说人话的那种，父亲会认真听完再开口的那种，朋友不会敷衍的那种」。
2. **结构**：加了一条「开头先接住一句」（贴着他说的话，不许用「我理解你的感受」这种客服腔）；
   建议从「一个小到可拒绝的下一步」升级成「**一个有分量的**建议」——具体到今晚能开个头、或指向他记录里的模式、或给一个值得问自己的问题。
   **仍然只给一个**（父母只给一句），仍然允许他拒绝。
3. **温度**：`temperature` 从全局写死 0.2 改成**按任务配**。抽取 0.2（要稳），对话 **0.7**，画像 0.5。
   这是主因之一——0.2 会一直选最安全的句式，读起来就是公文。

**顺带修的两个**
- 校验器只认 `YYYY-MM-DD`，而补记的旧事只有「大学期间」这种时间 → 把回答判成「没引用日期」。
  改成从上下文收集「时间标记」（记录开头那一段 + 4 位年份 + 日期的几种写法），命中任一即可。
- 上一轮加的「代表性检索」暴露出的显示问题：上下文里给模型看的还是时间戳。

**改完的实测（同一句「你觉得我能成功吗」）**
> 能不能成功，我不知道，谁也不敢替你打包票。但有几件事是写在记录里的：2024 和 2025 连续两年智能车队校内赛，
> 你都拿了校级二等奖——同一个比赛隔一年还愿意回去打，这种人不多了。……
> 说实话，你现在问「能不能成功」，说明心里已经有一件想做的事了，只是还没说出口。

**边界的把握**
温情 ≠ 空话。禁止清单一条没松：仍然不许「你已经很棒了」，仍然一次只给一条建议，仍然不许编造记录里没有的事。
松的只是**语气**和**结构**——从「列证据」改成「把证据揉进句子里，再给一句能做的话」。
